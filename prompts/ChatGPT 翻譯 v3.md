# ChatGPT 翻譯

## EU5 本地化翻譯規則

請依照以下規則，將 EU5 localization 翻譯為**台灣繁體中文**。

本規則的優先目標依序為：

1. 不漏 key、不重複 key、不破壞 source 順序。
2. 不破壞任何遊戲 token、placeholder、formatting tag 或 YAML/localization 結構。
3. 忠實保留原文效果、條件、因果、主詞、受詞、程度、時間關係與完整語意。
4. 正確辨識原文實際指涉、歷史文化身分、詞義、詞性與遊戲機制。
5. 正確套用目前唯一有效的 glossary。
6. **玩家可見的完整句、desc、事件敘述與短文章，首版譯文必須同時通過「語意忠實」「中文母語自然度」與「歷史文化語域適切性」三項硬性標準。即使譯文沒有錯譯，只要仍明顯保留英文語序、關係子句、名詞化、被動、介系詞結構或逐片語對應痕跡，或為追求現代中文自然度而抹除原有歷史制度、文化語感與時代詞彙，就不得視為完成，必須在首版輸出前重新組句。**
7. 在 glossary 未固定或需要 contextual 判斷時，依台灣繁體中文的既有譯名、專業資料與原文化語境，選擇自然、準確且符合成熟母語與歷史語域的譯法。不得以逐詞對應、保留來源語言句法或「文法上成立」作為譯文合格的標準。
8. 維持同一機制、同一事件組、同一實體與同一詞義的譯名一致性。
9. 維持同一事件組、同一敘事段落與相關 localization 的中文文體、語氣與用字品質一致。

不要整檔壓縮式翻譯。

desc、事件敘述、歷史敘事與短文章必須逐句理解原文資訊，不可摘要、概括或省略細節。

但必須嚴格區分：

> **逐句理解原意 ≠ 逐句照英文句型翻譯。**

忠實保留的是原文的**語意結構**，不是英文的**表面句法結構**。

只要完整保留原意、邏輯、條件、因果、程度與遊戲效果，中文可以而且應該依母語習慣：

* 調整語序。
* 拆句。
* 合句。
* 重組主從句。
* 改變修飾語位置。
* 將英文名詞化結構改成中文動詞結構。
* 將不自然的英文被動改為中文自然句式。
* 省略中文不需要重複的主詞或代詞。
* 必要時重新寫出中心名詞以避免代詞指涉不清。
* 將英文慣用語改寫成語意完全等價的自然中文。

不得把：

> 「最接近英文句子結構」

誤認為：

> 「最忠實的翻譯」。

## 一、最新 glossary 自動辨識

開始任何統計、拆 Batch 或翻譯之前，必須先從**目前可存取的 File Library 與本對話上傳檔案**中尋找所有可能的：

`translation_glossary*.yml`

並確定本次唯一有效的 glossary。

判定優先順序如下：

1. **使用者在目前對話中明確指定的版本**優先級最高。
2. 若使用者未明確指定，必須比較候選 glossary 的實際版本、內容與檔案 metadata，選擇**最新的實質版本**。
3. 若檔名含有版本時間戳，例如：
   `translation_glossary(YYYYMMDD-HHMMSS).yml`
   可作為版本判斷依據之一。
4. File Library 的 CreatedAt／ModifiedAt 可作為版本判斷依據，但不得僅因某份舊 glossary 被較晚重新上傳，就誤判成新版。
5. 若兩份 glossary 內容完全相同，只是檔名或重新上傳時間不同，視為同一實質版本，不得因較晚重新上傳而創造新的版本優先級。
6. 若專案 checkpoint、規則檔或其他可靠專案檔明確記載目前 authoritative glossary，可用來交叉驗證版本。
7. 若候選檔內容不同而版本先後仍無法可靠判定，不得混用；必須先自行進一步比對檔案內容、版本資訊與專案紀錄，再選出單一版本。

選定後：

* 本次工作只使用該 glossary。
* 所有更舊 glossary 一律忽略。
* 不得把多個 glossary 合併使用。
* 在同一次工作流程中不得自行切換 glossary。
* 若使用者之後明確指定更新版本，從後續工作起立即改用新版本，舊版本失效。

## 二、防漏翻／Parser 完整性檢查

在統計 key、判斷缺漏及拆 Batch 之前，必須先建立**完整 source key universe**，不得把單一 parser 或 regex 成功匹配到的結果直接視為本檔全部 localization key。

主要 localization parser 必須容許：

* 無縮排。
* 任意數量半形空格。
* Tab。
* 空格與 Tab 混合。
* 冒號前後合理的格式差異。
* 引號前後合理的格式差異。

不得只因縮排、Tab、空白或格式細節與主要 regex 不完全一致，就忽略 localization entry。

主要 parser 執行後，必須另外掃描**所有未匹配行**。

先排除：

* 空白行。
* 純註解行。
* localization 語言標頭。
* 已確認不是 localization entry 的其他合法結構。

剩餘未匹配行若具有任一特徵，必須列為疑似 localization key 並進一步檢查：

* 存在看似 `key:` 的結構。
* 冒號後存在雙引號 value。
* key 名稱符合一般 EU5 localization key 命名形式。
* 與前後 localization entry 結構高度相似。
* 僅因縮排、Tab、空白或格式差異未符合主要 regex。

若發現有效 localization key 未被主要 parser 匹配，必須：

1. 修正 parser 或加入 fallback parser。
2. 重新統計完整 source key。
3. 重新建立缺漏 key 清單。
4. 重新規劃尚未處理的 Batch。

在 parser 完整性確認前，不得正式拆 Batch 或翻譯。

## 三、Source／已翻譯／缺漏 key 集合完整性

必須建立：

* `source_keys`：完整英文 source 中所有 localization key。
* `translated_keys`：目前目標繁中檔中已存在且有效的 localization key。
* `missing_keys`：`source_keys` 中尚未存在於繁中檔的 key。

`missing_keys` 必須直接由完整集合計算：

`missing_keys = source_keys - translated_keys`

並驗證：

`translated_keys ∪ missing_keys == source_keys`

以及：

`source_keys - translated_keys - missing_keys == ∅`

初始統計必須滿足：

`已翻譯 key 數 + 缺漏 key 數 = source key 總數`

若任一等式不成立，先停止翻譯並重新檢查 parser／key 集合。

若繁中檔存在 source 中沒有的額外 key，應另外記錄檢查，但不得因此忽略真正缺漏的 source key。

不得只依：

* 舊 Batch 清單。
* 人工紀錄。
* Batch 編號。
* 前次聊天文字。
* 「前一批累計 + 本批行數」。

來推定真正進度。

---

## 四、Missing key、Source 順序與上下文

所有 `missing_keys` 必須保留其在 source 中的原始順序。

補翻 Batch 必須以 `missing_keys` 為基準，而不是把兩個缺漏 key 之間所有 source key 一律視為待翻譯內容。

若缺漏 key 之間存在已翻譯 key：

* 可以閱讀作為上下文。
* 不得重新輸出為本批新增翻譯。
* 不得重複計入進度。
* 除非使用者另有要求，不得覆蓋既有譯文。

若完整事件組只有部分 key 缺漏，可以閱讀整組 title/desc/option/tooltip，但最終補翻檔原則上只輸出缺漏 key。

每個 Batch 的：

* key 數 = 實際新增的 missing key 數。
* 起點 = 第一個實際 missing key。
* 終點 = 最後一個實際 missing key。

## 五、Batch 規劃與完整性

翻譯前先辨識：

* 完整事件組。
* title/desc/option/tooltip 關係。
* 共同 prefix。
* `_NAME/_DESC` 配對。
* 同一功能區段。
* 其他不可拆分的完整語意單位。

若需拆成多個 Batch，首次只提供拆批規劃，不直接翻譯。

拆批優先保持完整語意單位；不可為了湊 key 數拆散事件。

建議規模：

* 極短且同質 UI：50～80 key。
* 一般短句、簡短 tooltip、`_NAME/_DESC`：35～55 key。
* 中等機制說明或條件文字：20～40 key。
* 長 desc、事件敘述、歷史敘事、短文章：**6～12 key**。
* 高複雜度長 desc、多層條件／因果、多人稱指涉、高風險 placeholder：**4～8 key**，必要時更少。
* 若單一 key 本身即為數百字以上的文章型 localization，應依實際文字量降低 Batch 規模，必要時單批只處理 **1～4 key**，不得只依 key 數判斷負荷。

`50 key` 只是參考，不是固定目標。

原則上單一 Batch 不超過 80 key；若完整事件組本身超過建議規模，仍不得為湊 key 數而任意拆散完整事件。

若單一 key 本身已包含非常長的文章式 desc，應將該 key 視為高負荷翻譯單位，不得僅因 key 數少就與大量其他長文本塞入同一 Batch。

極短 UI 與大量長事件敘述不得單純為湊 Batch key 數而混合。

對長文本 Batch，目標不是最大化單批 key 數，而是讓每個文本都能在**首版輸出前**完成：

**完整理解 → 中文母語化重構 → 歷史文化語域校準 → 中文自我潤色 → 原文語意確認**

以上步驟屬於同一次翻譯流程中的內部處理，不另產生第二版譯文，也不需要另一輪 review。

Batch 規劃完成後必須驗證：

`所有 Batch key 的聯集 == missing_keys`

且：

`各 Batch key 彼此不得重複`

所有 Batch 的 key 數總和必須等於 `missing_keys` 總數。

若後續重新拆分或合併尚未處理 Batch，必須重新執行完整性檢查，並同步更新：

* Batch 清單。
* key 範圍。
* 總批次數。
* 累計完成。
* 尚未處理。
* 整體進度。

若後續發現「目前下一個 source key」與原 Batch 起點不一致，不得直接假設漏翻，也不得把中間所有 source key 都當成缺漏；必須重新比較 `source_keys`、`translated_keys`、`missing_keys`。

## 六、核心翻譯原則

* 以 localization 的**實際功能、實際指涉與玩家可見語義**為最高判斷基礎。
* 必須先判斷原文「實際指的是什麼」，再判斷「台灣繁中應該怎麼說」；不得把這兩個步驟顛倒。
* **忠實翻譯的是原文的意思，不是英文句子的外形。**
* 不得為了中文流暢而改變效果、條件、因果、主詞、受詞、時態、程度或邏輯。
* 但也不得以「忠實」為理由，保留在中文中不自然的英文語序、名詞化結構、被動結構、介系詞結構、關係子句結構或慣用語字面形式。
* desc 必須完整保留資訊，不可摘要，但可以依中文需要拆句、合句、重排資訊與重組句法。
* 同一英文詞在相同詞義、詞性、實體類型、機制與語境中應保持核心譯義一致。
* 同一英文詞在不同語境具有不同詞義或不同實體類型時，允許 contextual 翻譯，不得為了表面一致而犧牲原意。
* 優先使用成熟、自然的台灣繁體中文，不得只做簡體轉繁體。
* 「繁體中文」不等於「台灣繁體中文」；香港、澳門、一般繁體轉換及中國大陸用語轉成繁體後，均不得自動視為台灣標準用語。
* 官方簡中可作為機制理解、專名辨識或語義參考，但不得因官方簡中存在就自動照搬其用詞；仍須判斷台灣繁中自然度、歷史語境、文化指涉與實際機制。
* 若英文原文本身不自然、像內部工程文字、非母語英文或機械生成句型，應依 key、同組 localization 與實際機制重建其真正語義，再用自然中文表達；不得模仿英文病句。
* 不得擅自增加原文不存在的效果、身分、頭銜、因果、程度、歷史資訊或價值判斷。
* 不得因某個搜尋結果、百科標題或官方簡中譯名看起來方便，就跳過對原文實體、原語與歷史文化背景的確認。

### 中文母語品質標準

玩家可見的 desc、事件文字、歷史敘事與完整句子，不得只達到：

> 文法正確、看得懂、沒有明顯翻錯。

首版譯文應以以下標準為完成門檻：

> **如果拿掉英文 source，只讓台灣繁中母語者閱讀譯文，是否會覺得這原本就是以中文撰寫的歷史策略遊戲文本？**

**此項為完成條件，不是偏好或加分項。**

若答案為否，或仍可明顯由中文反推出英文原句的句法骨架，必須重新組句後才能輸出。

此時不得只做同義詞替換；應重新檢查整句的：

* 資訊順序。
* 主從關係。
* 中心動詞。
* 修飾範圍。
* 句子切分。
* 代詞銜接。
* 主動／被動選擇。

**中文句子的骨架可以與英文完全不同，只要原文實際命題、條件、因果、程度、時間關係與遊戲效果完全相同。**

如果仍明顯感覺是「照著英文結構翻出來的中文」，即使語意沒有明顯錯誤，也不視為完成。

成熟中文不代表華麗中文。

**成熟母語化也不等於現代化。**

EU5 屬於歷史策略遊戲。若 source 所描述的是前現代制度、官職、軍制、宗教、禮制、社會身分、政治倫理或歷史敘事，中文應採用與該時代和文化相稱的自然歷史語域。

不得為了讓句子「像現代中文」而把已有成熟歷史用語的概念改寫成現代行政、企業、法律、軍事或日常口語。

判斷標準不是：

> 現代台灣人日常會不會這樣說？

而是：

> **一名熟悉該時代與文化的成熟台灣繁中歷史文本編輯，在描寫這個時代、制度與文化時會不會這樣寫？**

目標應是：

* 自然。
* 清楚。
* 流暢。
* 精準。
* 有歷史策略遊戲的正式感。
* **中文文體強度應服從 source。**原文平實時，不得為增加「歷史感」而無故文言化、成語化或戲劇化；原文本身具有文學、宗教、政治宣言、諷刺、煽動或修辭色彩時，則應以自然台灣繁中等效保留其文體與感染力。
* 成語、典雅措辭與修辭並非禁止使用；只有在它們能自然且準確地表達 source 原有語氣時才使用，不得為了讓中文「看起來更漂亮」自行增加原文不存在的情緒、程度、價值判斷或意象。
* 成熟中文的目標是自然、準確且有合適文體，不是一律口語化，也不是一律文學化。
* 不留下明顯英文句法痕跡。
* 不因追求現代中文順口而抹除歷史制度、文化身分與時代語域。

原文平實時，中文應平實。

原文帶有文學、宗教、政治、宣傳、殘酷、諷刺或其他特定語氣時，中文才相應保留該語氣。

## 六之一、長句／desc／短文章的首版翻譯流程

所有：

* desc。
* event description。
* 歷史敘述。
* flavor text。
* 兩句以上的完整文字。
* 多層從句。
* 多層條件或因果。
* 明顯文章式 localization。

在產生首版譯文之前，內部必須依以下順序完成處理。

**不得輸出中間草稿、逐句分析或第二版翻譯。最終只輸出已完成母語化與歷史語域校準的首版結果。**

### Step 1：先理解整句，不急著翻字面

先確認：

* 誰是主詞。
* 誰是受詞。
* 發生什麼。
* 原因是什麼。
* 結果是什麼。
* 是否有條件。
* 是否有轉折。
* 是否有否定。
* 是否有數量或程度限制。
* 各代詞究竟指誰。
* 各修飾語實際修飾什麼。
* 原文句子的資訊焦點在哪裡。
* 原文語氣是正式、平實、宗教、政策、文學、煽動、威脅、殘酷或其他風格。
* 是否涉及特定歷史制度、文化身分、官職、宗教術語、軍制、禮制或其他前現代語域。

此階段的目的只是理解。

不得一邊讀英文，一邊逐片語建立固定中文對應。

---

### Step 2：脫離英文表面語序，以中文重構

確認完整意思後，再思考：

> 如果同樣內容原本就是由一名熟悉該時代與文化的成熟台灣繁中歷史策略遊戲文本編輯撰寫，他會怎麼寫？

可以依自然中文需要：

* 改變英文資訊出現順序。
* 將原因移到句首或句尾。
* 將目的結構改成中文自然結果句。
* 將過長英文句拆開。
* 將英文兩個短句合成自然中文句。
* 將關係子句轉成中文前置修飾或獨立句。
* 將抽象名詞改成動詞。
* 將英文形式被動改為中文自然主動句。
* 將英文慣用語改成中文等義表達。
* 省略不需要反覆出現的代詞。
* 為避免歧義重新寫出主體。
* 調整資訊焦點，使中文敘述自然。
* 將現代英文解釋詞還原為當時實際存在且可可靠確認的歷史制度或文化術語。

只要原文實際命題沒有改變，中文不需要逐句、逐片語與英文保持表面對應。

**自然化處理的是句法；歷史化處理的是詞彙、制度名稱與語域。兩者不得互相取代。**

---

### Step 3：進行一次「遮住 source」的中文母語編輯

首稿完成後，在同一次翻譯流程內部，**暫時將英文 source 視為不可見，只閱讀繁中譯文。**

此階段不是再次翻譯，而是檢查：

> **如果這段文字從一開始就是由一名熟悉該時代與文化的成熟台灣繁中歷史文本編輯撰寫，他真的會這樣寫嗎？**

若答案是否定的，即使所有英文資訊都有對應、文法正確且語意基本正確，也必須重新組句。

**不得因為某個中文字詞可以在英文原句中找到逐詞對應，就保留一個不自然的中文結構。**

此時只看中文本身，特別檢查：

* 是否有明顯英文語序。
* 是否有過多「……的……的……」。
* 是否出現中文不自然的被動。
* 是否保留英文名詞化結構。
* 是否把英文介系詞結構硬搬進中文。
* 是否有不必要的「進行」「使得」「對……予以」「將……置於」等翻譯腔。
* 是否可以用更直接的中文動詞表達。
* 代詞是否自然。
* 前後稱呼是否銜接。
* 是否因逐句翻譯導致句子彼此割裂。
* 是否存在「意思完全看得懂，但中文母語者通常不會如此寫」的片段。
* 是否出現過於拗口、過長或資訊排列不自然的句子。
* 是否有某句文體品質明顯低於同一事件組其他文字。
* 是否為追求「自然」而把古代制度、官職、軍制、宗教、禮制或政治語彙改成過度現代的行政／日常用詞。
* 是否為追求「歷史感」而反過度文言化、成語化或加入 source 不存在的古典修辭。

若存在更自然、歷史語域更合適且語意完全等價的中文寫法，**應直接在首版輸出前修正**。

這不是第二次 review，也不得另外輸出第二版。

---

### Step 4：母語化完成後再確認原文

完成中文重構後，再與 source 核對一次：

* 主詞是否相同。
* 受詞是否相同。
* 條件是否相同。
* 因果是否相同。
* 否定是否相同。
* 數量是否相同。
* 程度是否相同。
* 時間關係是否相同。
* 可能性／必然性是否相同。
* 遊戲效果是否相同。
* 是否有漏譯。
* 是否有自行補充。
* token 是否完整。

若自然中文與忠實語意發生衝突，忠實語意優先。

但不得因為要忠實，就直接退回英文句法直譯。

**此步驟只核對「原文與譯文的實際命題是否一致」，不得以逐詞對應程度、原句資訊順序、從句排列、修飾語位置或表面句法相似度作為忠實度標準。**

應重新尋找：

> **語意相同、中文也自然、歷史文化語域亦適切**

的寫法。

---

## 六之二、禁止「正確但翻譯腔」直接通過

以下情況即使：

* 文法正確。
* 中文看得懂。
* 基本意思沒有翻錯。

只要存在明顯英文句法痕跡，就仍須在首版輸出前改善。

例如：

英文：

`Those affected by the pest are dangerous, and their mere presence might spread the pestilence to the healthy, we must expel them from every community to give a chance to those that can still be saved.`

不佳但基本正確：

`染上疫病的人十分危險，僅僅是他們的存在就可能將瘟疫傳給健康的人。為了讓仍有機會獲救的人活下去，我們必須將病患逐出所有社群。`

這類譯文的問題不是主要語意錯誤，而是：

* `their mere presence` 機械映射成「僅僅是他們的存在」。
* `give a chance to...` 仍保留英文目的句結構。
* 前後稱呼從「染上疫病的人」突然換成「病患」，敘事銜接不夠自然。
* 整句仍看得出英文翻譯骨架。

較成熟的中文方向例如：

`感染疫病者十分危險，光是他們的存在就可能將瘟疫傳染給健康的人。我們必須將他們逐出所有聚落，給那些仍有機會得救的人一線生機。`

這個例子只用來說明**翻譯方法與中文品質標準**。

不得把其中：

* `pest`
* `pestilence`
* `community`
* `give a chance`

的譯法固定套用到所有其他上下文。

**例句中的中文句型本身也不是固定模板；不得因其被列為較佳示例，就在其他 desc 中大量仿用「光是……」「我們必須……」「一線生機」等結構。**

真正原則是：

> **不要逐片語找中文，而要先理解整句，再寫成熟中文。**

---

## 六之三、英文句法映射警示

以下不是 glossary，也不是固定翻譯表。

但長文本遇到以下類型時，必須特別警覺是否正在機械直譯：

* 關係子句：`which / that / whom / many of whom / those who / those that`
* 目的與原因結構：`in order to / so as to / with the purpose of / in return for`
* 抽象名詞化：`the increase of / the establishment of / the possibility of` 等
* 多層介系詞：連續 `of / with / by / in / for`
* 被動結構：`be affected by / be subject to / be regarded as`
* 虛主詞：`there is / there are / it is ... to`
* 英文抽象慣用搭配：`serve as / prove to be / make it possible to / give X a chance / mere presence`
* 多層關係子句。
* 英文抽象名詞連續堆疊。
* 多重被動。
* 多層 `of` 結構。
* `have X done`
* `find oneself...`

遇到這些結構時：

1. 先理解整句實際命題。
2. 再判斷台灣繁中自然資訊順序。
3. 依需要重新組織中文句法。
4. 不得先替每個英文片語找中文對應，再拼成句子。

核心原則：

> **先判斷整句命題 → 再依中文資訊結構重寫。**

---

## 六之四、不得只做同義詞替換式潤稿

改善中文品質時，不得只把：

`染上疫病的人`

換成：

`感染疫病的人`

然後保留整個英文句法骨架，就視為完成。

真正的母語化可能涉及：

* 整句語序。
* 句子切分。
* 資訊排列。
* 主從關係。
* 代詞銜接。
* 修飾範圍。
* 動詞選擇。
* 語氣。
* 中文資訊焦點。
* 前後句關聯。

首版翻譯目標不是：

> 每個英文片語都找到一個漂亮的中文片語。

而是：

> 整段中文讀起來本身就是成立的成熟中文文本。

---

## 六之五、自然化的邊界

自然化不等於自由改寫。

不得為了中文看起來漂亮而：

* 把 `might` 翻成確定事實。
* 把 `could` 翻成必然。
* 把 `many` 翻成全部。
* 把 `some` 翻成許多。
* 把 `40%` 自行翻成「至少40%」。
* 把普通「不滿」升級成「憤怒」。
* 把「可能威脅」改成「必將摧毀」。
* 新增原文沒有的歷史背景。
* 新增角色心理。
* 新增價值判斷。
* 自行合理化事件人物的行動。
* 替原文省略必要資訊。
* 因中文不喜歡重複，就刪除 source 實際刻意重複的強調。
* 為追求現代流暢感而把前現代制度改寫成現代政府、企業、行政、法律或軍事詞彙。
* 為追求歷史感而自行文言化、古典化或加入原文不存在的典故與修辭。

自然化的正確定義是：

> **用更自然的中文表達同一個命題。**

歷史語域校準的正確定義是：

> **用與該時代、制度與文化相稱的中文詞彙與文體表達同一個命題。**

---

## 六之六、同一事件組的敘事一致性

同一：

* event group。
* 事件鏈。
* 政策。
* 災難。
* 宗教事件。
* 外交事件。
* title/desc/option/tooltip 組合。

必須橫向閱讀。

除了術語一致以外，還需檢查：

* 敘事人稱是否一致。
* 正式程度是否一致。
* 同一概念是否無故在不同近義詞之間跳動。
* 同一人物／群體是否無故變換稱呼。
* 相鄰句是否因各自獨立翻譯而失去銜接。
* 是否有些句子像成熟中文，有些句子仍像逐字翻譯。
* 同組長 desc 是否呈現一致的語氣與品質。
* 同一事件組是否有某些句子突然現代化，而其他句子維持歷史語域。
* 同一歷史制度是否在不同句子中被一會兒譯成傳統術語、一會兒譯成現代功能詞。

例如同一疾病事件中：

* `sickness`
* `disease`
* `pest`
* `pestilence`

不得單純因英文字面不同就機械各自換不同中文。

但也不得為了表面一致把 source 真正有意區分的詞義抹除。

先判斷：

> 原文是真的語義不同，還是只是英文自然措辭變化？

再決定是否需要中文統一。

---

## 六之七、每個長文本都必須重新理解

即使同一 Batch 中有大量相似句型，也不得讓前一條譯文自動成為下一條的句法模板。

每個長 desc 都必須重新確認：

1. 原文實際語意。
2. 句子重心。
3. 中文自然資訊順序。
4. 與事件組其他文字的關係。
5. 專名與 glossary。
6. token。
7. 原文語氣。
8. 歷史文化語域。

只有 source 確實刻意使用平行句型，而且中文也適合平行呈現時，才保留高度相似句式。

不得因批量處理而大量產生：

* 同一句型。
* 相同開頭。
* 相同英文式轉折。
* 相同「為了……我們必須……」。
* 相同「……正日益……」。
* 相同「這將進一步……」。

除非原文確實要求如此。

---

## 七、Localization key／script context 輔助判義

localization key、script key、相鄰同組 key、NAME/DESC 配對及同功能區段可以作為**語義消歧證據**。

若英文 value：

* 文法不自然。
* 有多種可能解讀。
* 省略主詞或中心名詞。
* 無法判斷數值代表什麼。
* 無法判斷 scope 關係。

應優先檢查：

* localization key 名稱。
* positive／negative trigger 配對。
* FIRST／THIRD／NONE 等同組 trigger。
* `_NAME/_DESC`。
* 相鄰同機制 localization。
* placeholder 的實際資料類型。
* 同一功能的其他 UI／tooltip。
* 必要時查閱可取得的 EU5 腳本、遊戲文件或可靠外部資料。

但必須遵守：

* 玩家可見 source value 仍是主要翻譯對象。
* key 用來消歧，不是用來任意改寫 source。
* 不得翻譯或修改 key。
* 不得僅依 key 自行加入 value 與上下文都沒有支持的新資訊。
* 若 key 與 value 表面矛盾，應先以同組機制與實際遊戲功能判斷真正含義，不得靜默亂猜。

---

## 八、歷史文化語域與文化內生術語優先

**自然化處理的是句法；歷史化處理的是詞彙、制度名稱與文化語域。兩者不得互相取代。**

EU5 英文 localization 有時是把原文化中的制度、身分、官職、宗教概念或歷史稱謂先轉述成英文。

翻成繁中時，不得一律採：

`原文化概念 → 英文化解釋詞 → 中文逐字直譯`

應優先採：

`原文化概念／歷史制度 → 判斷實際身分與功能 → 尋找可靠既有中文名稱 → 再決定翻譯`

若某概念在其文化、歷史制度或台灣繁中史學中已有成熟、可靠、通行的名稱，優先使用文化內生術語、傳統漢字名稱或既有歷史譯名。

### 歷史語域不得被母語化抹平

中文母語化的目標，是消除來源語言句法痕跡，不是消除歷史語感。

對前現代中國及其他漢字文化圈文本，應優先判斷當時實際存在的：

* 官職。
* 官署。
* 爵位。
* 軍制。
* 賦役。
* 科舉與教育身分。
* 宗族與社會身分。
* 禮制。
* 宗教制度。
* 政治倫理。
* 文書種類。
* 朝廷用語。

若已有可靠歷史術語，應優先使用，而不得用現代功能對應詞取代。

例如：

* `minister` 在古代中國語境中不得自動譯為「部長」。
* `official` 不得一律譯為「官員」；若可確認具體官職、官僚身分或史學慣用稱呼，應依歷史制度處理。
* `court` 在中央政治語境中可為「朝廷」，不得因現代中文較常說「政府」就改成「政府」。
* `edict`、`memorial`、`tribute`、`levy`、`retainer` 等詞，若在歷史制度中有成熟中文對應，應優先使用歷史語彙，不得只採現代功能性意譯。
* 古代軍事制度不得只因英文使用 `army`、`guard`、`officer`、`minister`、`governor` 等現代可理解詞，就自動套入現代軍政語彙。

但歷史語域也不得過度古文化：

* 不得自行改成文言文。
* 不得大量加入 source 沒有的典故、成語或典雅措辭。
* 不得為製造「古代感」而使用不屬於該制度或時代的中國術語。
* 不得把其他文化功能相近的制度硬套成中國官制。
* 不得因為某個詞看起來「古雅」就優先於實際制度正確性。

正確目標是：

> **現代台灣繁中讀者能自然閱讀，但詞彙、制度名稱與文體仍符合其歷史文化語境。**

### 漢字文化圈特別規則

遇到中國、朝鮮、日本、越南及其他漢字文化圈文本時，必須特別判斷：

* 是否存在傳統漢字名稱。
* 是否存在台灣繁中或東亞史學慣用名稱。
* 英文是否只是對原制度的解釋性轉譯。
* 該詞在當時實際代表的官職、科名、階級、宗教職銜、禮制、軍制或社會身分。

不得因英文使用現代詞彙，就機械套用現代中文語域。

例如：

`Kējǔ graduate`

不得僅因 `graduate` 翻成「科舉畢業生」。

應先判斷實際科舉身分：

* 若只能確認為科舉出身者，可採「科舉出身士人」等保守譯法。
* 只有能確認其身分確為進士時，才可譯為「進士」。

`court`

* 若指東亞中央政治體系，可依語境使用「朝廷」。
* 若指君主身邊的廷臣圈、宮廷生活、宮廷文化，可使用「宮廷」。
* 不得一律固定成其中一種。

官職、爵位、科名、學官、宗教職銜、行政制度、禮制、軍制及社會身分若存在可靠傳統名稱，應優先採用歷史名稱，不得因英文表面使用 `graduate`、`official`、`minister`、`elder`、`governor` 等泛稱而自動採用現代直譯。

此規則**不是要求把所有東亞文本中國化**：

* 日本、朝鮮、越南等文化必須尊重其自身歷史制度。
* 不得把功能相似但實際不同的制度擅自套成中國官制、科舉、爵位或宗教制度。
* 不得為增加古典感而杜撰不存在的稱號。
* 不得僅因某名稱可寫成漢字，就假定該漢字形式是歷史真名。

### 一般文化內生術語

同一原則亦適用於：

* 伊斯蘭文化。
* 印度文化。
* 拜占庭／東羅馬。
* 斯拉夫文化。
* 非洲各文化。
* 美洲原住民族。
* 大洋洲及其他地區。

若原文刻意保留原語詞，例如 `Kējǔ`、`Strojnici`、`Kami` 等，通常代表文化特異性重要，必須特別檢查是否應：

* 還原既有中文名稱。
* 採歷史慣用譯名。
* 採可靠音譯。
* 音譯並由原文本身已有的解釋性文字協助玩家理解。
* 保留原文化特異性。

不得直接以泛化現代中文詞抹除文化背景。

若只能確認大致功能、無法確認精確歷史身分，採**語義透明、保守、不假裝過度考證**的譯法。

### 專名中的音界號「·」

不得因原文存在空格、連字號或多個外語單詞，就機械在中文音譯中加入音界號 `·`。

判斷原則如下：

* 人名中的姓名成分、複合個人名或具名神祇的多個名稱成分，若台灣繁中慣例適合，可使用 `·`。
* 宗教名稱、文化名稱、民族名稱、國名、地名、制度名稱、教團名稱及一般複合專名，原則上不得僅因原文有空格而加入 `·`。
* 若已有成熟台灣繁中譯名，音界號使用方式服從既有慣例。
* 音界號用來協助區分中文專名成分，不是用來逐一重現原文單詞邊界。

例如：

* 神祇／人物專名可依慣例使用 `·`。
* 宗教名稱不得因原文是兩個詞，就自動寫成「甲·乙信仰」。
* 地名、國名及文化名不得因英文有空格而逐詞加 `·`。

---

## 九、台灣繁中術語與外部資料查證優先順序

術語與專名查證必須分成兩個不同階段：

1. **確認原文實際指涉與語義。**
2. **確認該實體在台灣繁體中文中應使用什麼名稱。**

不得因先找到某個中文譯名，就反過來假定原文一定指該實體。

### A. 原文實際指涉與語義的查證順序

遇到不熟悉、多義、歷史性或文化特異的詞時，依以下順序確認原文實際指涉：

1. **EU5 本身的完整上下文**

   * localization value。
   * localization key。
   * script key。
   * NAME/DESC 配對。
   * 同組 tooltip。
   * 相關宗教、文化、國家、人物或遊戲機制。
   * 同一功能的其他 localization。

2. **原語與第一手／文化內部資料**

   * 原始語言詞典。
   * 歷史史料。
   * 宗教或文化自身機構。
   * 當地政府、博物館、文化保存機構。
   * 原民族／原文化自身資料。

3. **可靠學術與專業資料**

   * 學術論文。
   * 大學研究。
   * 專業辭典。
   * 權威資料庫。
   * 宗教學、歷史學、人類學、語言學等專業來源。

4. **可靠百科與其他二手資料**

5. **其他可合理輔助判斷的來源**

不得只依：

* 英文拼寫。
* 英文 Wikipedia 標題。
* 搜尋結果摘要。
* 某一份中文譯名。
* 官方簡中名稱。

判斷原文真正指涉。

若不同可靠資料對原文實體的身分、名稱或語義互相衝突，必須優先採用與 EU5 時代、地域、文化、宗教與實際遊戲機制最吻合的解釋。

### B. 台灣繁體中文譯名的選擇順序

在原文實際指涉已確認後，依以下順序選擇台灣繁中譯名：

1. **目前唯一有效 glossary 中語義適用的固定譯名。**
2. **台灣政府、教育、學術、文化、宗教及其他相關專業機構使用的穩定譯名。**
3. **台灣學術出版物、專業出版品及具有穩定慣例的台灣資料。**
4. **中文維基百科「臺灣正體（zh-tw）」顯示的譯名。**
5. **香港、澳門及其他可靠繁體中文資料。**
6. **若沒有可靠既有中文譯名，依原語實際發音、歷史形式、文化背景與台灣繁中音譯慣例自行翻譯。**
7. **簡體中文資料只作輔助參考，不得直接簡轉繁後視為台灣標準譯名。**

上述第 1 項的「glossary 固定譯名優先」必須符合：

* 當前語義相同。
* 實際指涉相同。
* 實體類型相同或 glossary 已明確設計為可 contextual 套用。

若 glossary 固定譯名與新查到的台灣資料不同，但 glossary 在當前語義中確實適用：

* 本次翻譯仍使用 glossary 固定譯名。
* 不得自行靜默修改 glossary。
* 可在內部標記為待人工檢討。
* 只有使用者明確裁定更新 glossary 後，後續翻譯才改用新譯名。

若 glossary 只是字面命中，但實際指涉不同，則不得因「固定譯名優先」而錯套。

### C. 中文維基百科「臺灣正體」規則

使用中文維基百科查詢台灣慣用譯名時，必須明確確認：

> **臺灣正體／zh-tw**

所顯示的頁面文字與名稱。

不得只看：

* 搜尋引擎結果標題。
* 中文維基百科未指定地區版本的頁面標題。
* 原始條目名稱。
* 簡體中文版。
* 「繁體」但未確認是否為臺灣正體的版本。
* 自動簡繁轉換後看似繁體的文字。

必須認知：

> **中文維基百科的原始條目名稱、一般繁體顯示與「臺灣正體（zh-tw）」顯示結果可能不同。**

因此：

* 若中文維基百科被用來判斷台灣譯名，必須實際檢查臺灣正體顯示結果。
* 若臺灣正體版本與簡體／一般版本使用不同譯名，不得把簡體或一般版本優先於臺灣正體。
* 若臺灣正體 Wikipedia 與台灣政府、學術、專業或相關宗教／文化機構資料衝突，優先採較高品質、較專業且更貼近實際語境的台灣來源。
* Wikipedia 是重要參考來源，但不是最高權威。
* 不得因 Wikipedia 有一個中文名稱，就忽略該名稱是否屬於不同人物、不同神祇、不同時代或不同文化實體。

### D. 簡體中文資料的使用限制

簡體中文資料可用於：

* 辨認某一專名可能指誰。
* 查找原語拼法。
* 查找其他語言資料線索。
* 理解中國大陸的既有譯名。
* 比較不同漢譯傳統。
* 輔助判斷官方簡中的翻譯邏輯。

但不得：

* 直接簡轉繁後作為台灣譯名。
* 因官方簡中已有譯名就自動視為固定譯名。
* 因簡體資料搜尋結果較多，就壓過台灣既有譯名。
* 把中國大陸特有的人名、地名、宗教、歷史或專業譯法直接視為台灣慣例。

若台灣無固定譯名，而簡體中文已有成熟譯名：

* 可作重要參考。
* 仍必須回到原語、實際發音與台灣音譯慣例重新判斷。
* 不得只做字形轉換。

### E. 不同領域的專業來源

若屬於特定專業領域，應優先檢查該領域在台灣的權威或專業資料，例如：

* 天主教：梵蒂岡繁體中文、台灣天主教會及相關專業資料。
* 基督宗教：台灣神學研究、教會史與相關專業資料。
* 佛教、梵語、巴利語：佛典、DILA、佛學辭典、台灣佛學研究。
* 伊斯蘭：台灣伊斯蘭研究、學術資料及可靠宗教史資料。
* 歷史地名：台灣政府、國教院、歷史研究、地理專業資料。
* 民族與語言：國教院、中研院、台灣民族學／語言學研究及相關官方資料。
* 動植物：台灣官方名錄、學術機構及專業分類資料。
* 歷史制度、官職與爵位：台灣歷史學、制度史及相關專業研究。

不得用低品質百科、旅遊網站或搜尋結果摘要壓過更高品質的專業來源。

## 十、Glossary 使用規則

翻譯前必須掃描本批原文中的 glossary 命中。

使用：

**longest match first**

完整片語優先於其中單字。

但 longest match first 只決定優先檢查順序，不代表命中詞條一定適用。

每個命中必須判斷：

* 詞義。
* 詞性。
* 完整片語。
* 上下文。
* 歷史／文化身分。
* 遊戲機制。
* 實際指涉。
* 實體類型。

glossary 若已區分：

* 固定譯名。
* 參考譯義。
* 候選譯名。
* 其他類型。

必須遵守其分類，不得全部當成固定譯名。

對**語義與實際指涉均適用的固定譯名**，優先級最高，必須套用。

固定譯名的優先級是在**已確認原文確實指向同一概念／實體**之後成立；不得利用 glossary 反過來強行決定原文指涉。

若 glossary 值列有多個候選譯名，不得把候選整串放進譯文；必須依語境選一個最適合者。

若只是字面命中但詞義不同：

`詞義不適用`

不得強制套用。

若命中只位於：

* `$...$`
* `[...]`
* `@...!`
* script key
* localization key

則 token/key 本身不可翻譯，該命中屬：

`受保護 token/key，不適用`

但 `#...#!` 不得整體視為受保護 token；tag 內玩家可見文字仍須正常 glossary 掃描。

### Glossary 詞形／詞族正規化

glossary 比對不得僅限於與 glossary key 完全一致的字面形式。

對一般英文詞彙，應進行**詞形正規化與語義詞族辨識**，判斷正文中的詞是否屬於 glossary 已定義詞條的：

* 規則性屈折變化。
* 不規則屈折變化。
* 常見派生形式。
* 明確且可靠的語義詞族。

此規則的目的，是讓 glossary 中的核心詞條能正確涵蓋其自然語言中的合理變體；但**詞族相關不代表所有形式必須機械套用完全相同的中文字串**。

#### A. 大小寫變體

大小寫差異原則上不得阻止 glossary 命中。

例如 glossary：

`Bishop → 主教`

正文中的：

* `Bishop`
* `bishop`
* `BISHOP`

若詞義相同，均應視為同一核心詞條。

但若大小寫具有專名／普通名詞等實際語義差異，仍須依上下文判斷。

#### B. 單複數與所有格

應辨識：

* 單數。
* 規則複數 `-s`。
* 規則複數 `-es`。
* `-ies` 等常見拼寫變化。
* 所有格 `'s`。
* 複數所有格 `s'`。
* 不規則複數。

例如 glossary：

`Bishop → 主教`

則在相同詞義下：

* `bishop`
* `Bishops`
* `bishops`
* `Bishop's`
* `bishop's`
* `Bishops'`

均應追溯至 `Bishop` 核心詞條。

不規則形式亦應依語義辨識，例如：

* `man → men`
* `woman → women`
* `person → people`
* `child → children`

不得只依是否能機械去除 `s/es` 判定 glossary 命中。

#### C. 動詞屈折與時態

若 glossary 收錄的是動詞基本形，應辨識其合理屈折變化，包括：

* 第三人稱單數。
* 過去式。
* 過去分詞。
* 現在分詞／動名詞。
* 常見不規則時態。

例如核心詞若為：

`convert`

則應能辨識：

* `converts`
* `converted`
* `converting`

但詞形辨識只表示它們屬於同一核心動詞；實際繁中仍須依時態、語態及句法自然翻譯，不得忽略原文時間與狀態差異。

#### D. 形容詞比較級與最高級

若 glossary 收錄形容詞基本形，應辨識：

* `-er`
* `-est`
* `more + adjective`
* `most + adjective`
* 不規則比較級／最高級。

例如：

`strong`
`stronger`
`strongest`

應辨識為同一形容詞核心概念，但繁中譯文仍須保留比較或最高程度的語義。

#### E. 國名、地名、居民名、民族名、文化名、語言名與形容詞

應辨識同一地理／文化概念家族中常見的派生形式，包括但不限於：

* `-n`
* `-an`
* `-ian`
* `-ese`
* `-i`
* `-ish`
* `-ic`
* `-ite`
* `-ine`

例如可能存在：

* `Rome → Roman`
* `Italy → Italian`
* `Arabia → Arabian`
* `Iraq → Iraqi`
* `Japan → Japanese`
* `Israel → Israeli`
* `England → English`
* `Scotland → Scottish`

亦必須注意完全或高度不規則的關係，例如：

* `France → French`
* `Netherlands → Dutch`

這類關係不能只靠字尾 stemming 推導；若語義與上下文明確顯示為同一地理／文化概念家族，應進行語義辨識。

但不得因此假定：

* 國名。
* 文化名。
* 居民名。
* 民族名。
* 語言名。
* 形容詞。

在中文中一定使用完全相同形式。

必須依 source 實際指涉判斷中心名詞是否需要：

* 人。
* 文化。
* 語。
* 式。
* 的。
* 其他適當形式。

#### F. 宗教、思想、學派及其詞族

應辨識宗教、思想與學派名稱及其：

* 信徒。
* 支持者。
* 學派成員。
* 形容詞。
* 思想／主義名稱。

常見詞尾包括：

* `-ism`
* `-ist`
* `-istic`
* `-ian`
* `-ite`

例如 glossary：

`Calvinism → 喀爾文主義`

則：

* `Calvinist`
* `Calvinists`
* `Calvinistic`

應辨識為與 `Calvinism` 相關的詞族。

但實際中文須依語境區分，例如：

* `Calvinism` → `喀爾文主義`
* `Calvinist` → `喀爾文主義者`／`喀爾文派`
* `Calvinistic` → `喀爾文主義的`

不得全部機械翻成「喀爾文主義」。

亦必須辨識不規則宗教詞族，例如：

* `Islam`
* `Muslim`
* `Islamic`

三者具有明確語義關聯，但不是單純 suffix 變化。

同理：

* 宗教本身。
* 信徒。
* 宗教形容詞。
* 教派。
* 制度。

不可因屬於同一詞族就忽略實體類型差異。

若 EU5 的 localization 結構明確顯示某 `-ist`、`Pagan`、`Mandaean`、`Manichaean` 等形式只是 religion adjective，而不是「一名信徒」，中文不必為了模仿英文詞形而強行加「……者」。

例如：

* religion 名稱與 religion adjective 在中文可自然使用相同譯文。
* 只有實際表示人物／信徒時，才翻成「……信徒／……者」。

#### G. 人物、從業者、支持者、信徒與成員派生

常見人物／群體後綴包括：

* `-er`
* `-or`
* `-ist`
* `-ian`
* `-ite`
* `-ant`
* `-ent`

應辨識其與核心詞條的關聯。

但不得機械把所有此類形式翻成「……者」。

應依實際歷史、文化、宗教及機制語境判斷其可能是：

* 官職。
* 職業。
* 身分。
* 信徒。
* 黨派。
* 學派成員。
* 民族／居民。
* 政治支持者。
* 一般施事者。

#### H. 常見形容詞派生

應注意常見形容詞後綴，例如：

* `-al`
* `-ial`
* `-ic`
* `-ical`
* `-ous`
* `-ary`
* `-ive`
* `-ian`
* `-ish`
* `-ine`

例如：

* `colony → colonial`
* `empire → imperial`
* `republic → republican`
* `religion → religious`

這類詞可屬於同一概念家族，但派生後的詞性與語法功能已改變。

不得直接把名詞 glossary 譯名原封不動套入形容詞位置；必須依中文語序與語義自然調整。

#### I. 常見名詞派生

應注意常見名詞派生後綴，包括：

* `-ity`
* `-ness`
* `-hood`
* `-ship`
* `-dom`
* `-cy`
* `-tion`
* `-sion`
* `-ment`
* `-ance`
* `-ence`

例如：

* `brother → brotherhood`
* `citizen → citizenship`
* `king → kingdom`

這類詞可能與 glossary 核心詞相關，但通常已形成新的中心概念。

因此：

* 可以用核心 glossary 詞條作語義參考。
* 不得自動要求派生詞使用相同中文字串。
* 若派生詞本身已有 glossary 詞條，必須優先使用派生詞的完整詞條。

#### J. 制度、轄區、領域與職位體系派生

EU5 歷史制度詞中特別注意：

* `-ric`
* `-ate`
* `-dom`
* `-ship`
* `-cy`
* `-hood`

例如：

`Bishop → Bishopric`

兩者雖有詞族關係，但：

* `Bishop` 是人物／宗教職位。
* `Bishopric` 可能是主教職、主教區或相關制度／轄區。

不得因 glossary 有：

`Bishop → 主教`

就把：

`Bishopric`

機械譯成「主教」。

同理：

* `Patriarch → Patriarchate`
* `Emir → Emirate`

等情況都必須依派生後的實體類型重新判斷。

#### K. 常見前綴派生

應辨識常見前綴與 glossary 核心詞的關聯，例如：

* `anti-`
* `pro-`
* `neo-`
* `post-`
* `pre-`
* `non-`
* `ex-`
* `counter-`
* `re-`
* `de-`
* `un-`

例如：

* `Catholic → anti-Catholic`
* `colonial → post-colonial`
* `reform → counter-reform`

核心 glossary 詞條可作為派生詞翻譯基礎，但前綴的否定、時間、立場、反對、重新等語義必須完整保留。

不得只抓到核心詞後忽略前綴。

#### L. 連字號、空格與正字法變體

應辨識不改變實際詞義的常見形式差異，例如：

* 有／無連字號。
* 有／無空格。
* 大小寫。
* 複合詞拼寫差異。
* 英美拼字差異。
* 合理的歷史正字法差異。

例如：

* `Prince-Bishop`
* `Prince Bishop`
* `prince-bishop`

在實際語義相同時，可視為同一詞條候選形式。

但只有在確定實際指涉相同時才可正規化，不得僅因字串相近就合併。

#### M. 歷史拼寫、轉寫與羅馬化變體

歷史、宗教、人物與文化專名可能存在：

* 有／無變音符號。
* 不同拉丁化。
* 不同羅馬化系統。
* `æ/ae` 等正字法差異。
* `š/sh`、`č/ch` 等轉寫差異。
* 同一名稱的歷史拼寫變體。

若有可靠證據顯示為同一實體或同一概念，可視為 glossary 詞條的相關形式。

但此類比一般屈折變化風險更高，必須保守處理。

不得僅靠字串近似度自動把兩個專名視為同一詞條。

#### N. 詞族辨識與翻譯套用的區別

必須嚴格區分：

**「屬於同一詞族」**

與

**「必須使用完全相同的中文譯名」**

兩者不是同一件事。

詞族辨識只表示：

1. 應檢查 glossary 中的相關核心詞條。
2. 應保留 glossary 已確立的核心概念。
3. 應避免同一概念因單複數、大小寫或自然派生而無故改用完全不相關譯名。

但若派生造成：

* 詞性改變。
* 中心名詞改變。
* 人物變制度。
* 地名變居民名。
* 宗教變信徒。
* 主義變支持者。
* 名詞變形容詞。
* 國名變語言名。
* 實體類型改變。

則必須依實際語義重新構成自然繁中。

#### O. 完整詞條優先

若 glossary 中同時存在：

* 基礎詞條。
* 派生詞條。
* 複合詞。
* 完整片語。

則必須遵守：

**完整 glossary 詞條 > 完整片語 > 明確派生詞條 > 核心詞族推導**

例如 glossary 同時有：

`Bishop`
`Prince-Bishop`
`Bishopric`

正文出現：

`Prince-Bishop`

必須優先匹配 `Prince-Bishop`。

不得因其中含有 `Bishop`，先套用 `Bishop` 再自行拼湊。

正文出現：

`Bishopric`

若 glossary 本身已有 `Bishopric`，亦必須優先使用該完整詞條。

#### P. 詞族規則不得覆蓋語義判斷

詞族正規化仍必須服從：

* longest match first。
* 完整片語優先。
* glossary 詞條類型。
* 當前詞義。
* 詞性。
* 實體類型。
* 歷史文化語境。
* 遊戲機制。
* localization key／script context。
* contextual／語義衝突規則。

不得僅因兩個詞：

* 字根相同。
* 字首相同。
* 字尾相似。
* spelling 相近。

就自動認定為同一 glossary 詞義。

若關係不明確，應視為「可能相關詞族」進一步判斷，而不是為了增加 glossary 命中率強行套用。

### Glossary contextual／語義衝突

固定譯名優先，但前提是**當前語境中確實指同一概念、同一實體與相容的實體類型**。

若直接套用 glossary 會造成：

* 地點被翻成文件。
* 人物被翻成制度。
* 制度被翻成物件。
* 宗教被翻成神祇。
* 神祇被翻成宗教。
* 民族被翻成語言。
* 實體類型明顯錯置。
* 中文句意在現實或遊戲機制上不可能成立。

不得機械硬套。

應先判斷：

1. 是否其實是不同詞義。
2. 是否該英文詞在當前語境發生 metonymy／轉喻。
3. 是否 glossary 本身需要 contextual 使用。
4. 是否能透過同組 key、script 或遊戲機制確認實際指涉。

確認後應採取**能忠實表達實際指涉、又最大程度保留既有術語核心**的 contextual 譯法。

不得只因 glossary 存在就產生明顯不通的中文。

同時不得靜默把 glossary 的固定術語整體永久改名；本批 contextual 處理不等於修改 glossary 本身。

## 十一、Comparator／數值 Trigger 規則

`$COMPARATOR$` 與其後比較值通常構成完整比較條件，中文原則上直接相連：

`$COMPARATOR$$NUM|...$`

不得因英文空格而保留：

`$COMPARATOR$ $NUM$`

若負向 trigger 原文是：

`does NOT have $COMPARATOR$ $NUM$ ...`

不得機械翻成：

`沒有$COMPARATOR$$NUM$個……`

因 `$COMPARATOR$` 可能展開為：

* 大於。
* 小於。
* 至少。
* 至多。
* 等於。
* 其他比較形式。

翻譯必須對所有合理展開結果都成立。

對數值 trigger，優先依實際指標重組，例如：

* `……數量並非$COMPARATOR$$NUM$`
* `……總數並非$COMPARATOR$$NUM$`
* `……總值並非$COMPARATOR$$NUM$`
* `……比例並非$COMPARATOR$$NUM$`
* `……等級並非$COMPARATOR$$NUM$`
* `……進度並非$COMPARATOR$$NUM$`

若原文為 `can NOT`：

* 表達能力不足、條件不成立 → 優先「無法」。
* 表達規則禁止、不允許 → 優先「不可／不允許」。

不得為了形式一致，把所有否定 trigger 一律機械改成同一句型。

---

## 十二、Every 的處理

`every` 不得機械翻成「每個／每一個」。

當 `every + 複數或集合實體` 表示範圍內無一例外時，繁中優先：

* 所有……
* 全部……
* ……均……
* ……都……

例如：

`Every neighboring country`
→ `所有鄰近國家`

`Every estate loses influence`
→ `所有階層的影響力都會降低`

只有在強調逐一分配、個別套用或週期頻率時使用「每……」：

* `Every character receives...` → `每名角色都會獲得……`
* `Every month` → `每月`
* `Every time` → `每次`
* `Every 5 years` → `每5年`

判斷：

* 全體集合 → 所有／全部／均／都。
* 每個個體分別受效果 → 每名／每個／各。
* 頻率 → 每月／每次／每N年。

## 十三、受保護 token 與格式

必須保留：

* localization key。
* key 順序。
* 必要縮排。
* YAML/localization 結構。
* `\n`
* `$...$`
* `[...]`
* `@...!`
* formatting tag 的控制語法與結構。
* script key。
* localization key。

`$...$`、`[...]`、`@...!` 內容不得翻譯或修改。

普通英文空格不是遊戲語法；翻譯後依繁中排版處理。

一般中文標點使用全形。

一般斜線分隔：

`/`

不得使用：

`／`

斜線兩側不加空格。

英文 dash 若作分類或標題分隔，可譯為：

`——`

## 十四、Formatting tag 內可見文字

`#...#!` 不得整體視為不可翻譯 token。

必須拆成：

1. 開頭格式控制碼，例如 `#italic `、`#T `、`#Y `。
2. tag 內玩家可見文字。
3. 結尾 `#!`。

只有控制碼與結構受保護。

tag 內玩家可見文字必須正常：

* 翻譯。
* glossary 掃描。
* 專名判斷。
* 音譯。
* 歷史制度判斷。

不得因文字位於：

* `#italic ...#!`
* `#bold ...#!`
* `#T ...#!`
* `#Y ...#!`
* `#G ...#!`
* `#R ...#!`

就保留英文或其他外語。

例如：

`#T Important Offices#!`
→ `#T 重要職位#!`

`#Y Sea#!`
→ `#Y 海域#!`

`#italic Kapı Ağası#!`
→ `#italic [Kapı Ağası 的正確繁中譯名]#!`

不得把翻譯放在 tag 外而保留 tag 內原文。

若 tag 內只有 `$...$`、`[...]`、`@...!`、數字或符號，只保護這些內容本身。

翻譯後必須保持：

* tag 類型一致。
* 開啟／關閉數量一致。
* `#!` 完整。
* 巢狀結構一致。
* 控制語法未遭破壞。
* formatting tag 控制語法所需空格保留。

## 十五、角色代名詞 placeholder

`[...GetHerHis]`、`[...GetHisHer]` 等英文所有格代名詞 placeholder，在本專案繁中輸出中只會產生「他／她」，**絕對不自帶「的」**。

因此，翻譯時必須先把 placeholder 視為實際輸出的「他／她」，再依完成後的中文句法判斷是否需要補「的」。

不得：

* 誤以為 placeholder 本身會輸出「他的／她的」。
* 因英文 source 使用所有格，就不經中文句法判斷直接省略「的」。
* 反過來對所有所有格 placeholder 一律機械補「的」。

### 一般領屬名詞組

若 placeholder 在中文中直接作為一般名詞的領屬者，而省略「的」後會形成不自然的「他＋名詞／她＋名詞」結構，必須補「的」。

例如：

`[target_character.GetHerHis] loyalty`
→ `[target_character.GetHerHis]的忠誠`

`[target_character.GetHerHis] head`
→ `[target_character.GetHerHis]的頭顱`

`[target_character.GetHerHis] life`
→ `[target_character.GetHerHis]的性命`

`[target_character.GetHerHis] crimes`
→ `[target_character.GetHerHis]的罪行`

`[target_character.GetHerHis] schemes`
→ `[target_character.GetHerHis]的陰謀`

例如：

`Off with [target_character.GetHerHis] head!`
→ `砍下[target_character.GetHerHis]的頭顱！`

不得譯成：

`砍下[target_character.GetHerHis]頭顱！`

因為 placeholder 若實際輸出「他／她」，後者會顯示為不自然的「砍下他頭顱／砍下她頭顱」。

#### 中文慣用的無「的」結構

只有當完成後的中文本身具有自然且成熟的省略「的」結構時，才可省略。

例如：

`in [target_character.GetHerHis] hand`
→ `在[target_character.GetHerHis]手中`

`on [target_character.GetHerHis] shoulders`
→ `在[target_character.GetHerHis]肩上`

`before [target_character.GetHerHis] eyes`
→ `在[target_character.GetHerHis]眼前`

此處省略「的」的原因是中文本身的慣用句法，而不是因為 `hand / shoulders / eyes` 屬於身體部位。

不得把上述例外泛化成：

「身體部位前一律不加『的』」。

### 實際輸出替換檢查

對所有 `GetHerHis`／`GetHisHer` 所有格 placeholder，QA 時必須暫時將 placeholder 分別替換成：

`他`
`她`

並閱讀完整繁中句子。

若替換後產生：

`他頭顱`
`她性命`
`他陰謀`
`她罪行`

等不自然的直接領屬結構，表示缺少「的」，必須在輸出前修正。

若替換後為：

`在他手中`
`在她肩上`
`他眼前`

等自然中文結構，則可以不加「的」。

判斷標準永遠是 placeholder 實際展開後的完整繁中句子是否自然、清楚且語法成立，而不是英文是否使用 possessive form。

## 十六、GetFlavorRank

`[...GetFlavorRank]` 會輸出依國家、政體、文化、政府形式與當前等級變化的完整特色化稱號。

不得預設它一定是：

* 王國。
* 共和國。
* 帝國。
* 國家。
* 政權。

必須把整個 placeholder 視為可直接充當主詞、受詞或名詞成分的完整稱號。

不得：

* 刪除 placeholder。
* 固定翻成某一稱號。
* 在前後加入可能與實際輸出重複的「國家」「政權」「我國」等中心名詞。

英文 `the [...GetFlavorRank]` 通常可直接譯為 placeholder。

英文 `our [...GetFlavorRank]` 依語境可使用：

* `我們的[...GetFlavorRank]`
* `本[...GetFlavorRank]`
* 或自然重組句子。

## 十七、一般概念 token 的中心名詞

`[country|e]`、`[location|e]`、`[culture|e]`、`[religion|e]`、`[capital|e]`、`[market|e]` 等概念 token，在繁中 localization 中通常已會顯示完整中心名詞。

不得在 token 前後再補同義中心名詞造成重複。

例如：

`our [country|e]`
→ `我們的[country|e]`

不得：

`我國[country|e]`
`我方[country|e]`
`我們的國家[country|e]`

同理須檢查：

* `國家[country|e]`
* `首都[capital|e]`
* `市場[market|e]`

等是否會產生重複中心名詞。

若中文自然語序需要調整，優先重組句子，但必須保留原 token。

## 十八、文化名稱 placeholder

`[...GetCulture.GetName]`、`[...GetCulture.GetNameWithNoTooltip]` 通常只輸出文化名稱，不自帶「人」。

當英文 `a/an + [Culture placeholder]` 是指某文化背景的人時，中文必須補出中心名詞，通常：

`一名[Culture placeholder]人`

若原文指文化本身，不得補「人」。

## 十九、語言與方言 placeholder

本專案中：

* `GetCommonLanguage.GetName`
* `GetLanguage.GetName`
* `GetDialect.GetName`
* `GetDialect.GetNameWithNoTooltip`
* 各類 `dialect.GetNameWithNoTooltip`

其繁中輸出本身已包含「語」。

例如：

* 法語。
* 希臘語。
* 諾曼語。

因此 placeholder 後不得再加：

* 語。
* 語言。
* 方言。

即使英文寫：

`[placeholder] language`
`[placeholder] dialect`

中文也必須省略重複中心名詞或重組句子。

錯誤：

`[placeholder]語`
`[placeholder]語言`
`[placeholder]方言`

`GetName` 與 `GetNameWithNoTooltip` 只影響 tooltip，不影響此規則。

不得把語言／方言 placeholder 誤解成文化、民族或國籍。

## 二十、Placeholder/token 邊界空格

localization value 中普通英文空格不必逐字保留。

若 placeholder、variable、數字 token、tooltip token 與中文共同構成同一：

* 詞語。
* 名稱。
* 數量。
* 修正名稱。
* 語法成分。

必須直接相連，不得保留或新增半形空格。

例如：

`$survive_string$ [target_location_2.GetArea.GetName]`
→ `$survive_string$[target_location_2.GetArea.GetName]`

`[ShowModifier('warrior_banners_modifier')] [modifier|e]`
→ `[ShowModifier('warrior_banners_modifier')][modifier|e]`

`[target_character.GetName] years old`
→ `[target_character.GetName]歲`

`#G +100#! [prestige|e]`
→ `#G +100#![prestige|e]`

但 formatting tag 控制語法內必要空格必須保留：

`#G +100#!`

不得改壞。

## 二十一、人名、歷史人物、作品與 music_player

歷史人物、君主、宗教人物、事件人物：

* glossary 有語義適用固定譯名 → 使用 glossary。
* glossary 未固定時，先確認人物實際身分。
* 有台灣繁中通行譯名 → 優先採用台灣通行譯名。
* 查詢中文維基百科時，若用於判斷台灣譯名，必須確認「臺灣正體（zh-tw）」顯示結果。
* 無既有譯名 → 依原語、歷史語境與台灣繁中慣例音譯。
* 不得只做簡體轉繁體。
* 不得把無法確認的歷史人物硬套成另一位同名人物。
* 不得因中國大陸簡中資料使用某一音譯，就在未檢查台灣用法的情況下直接簡轉繁採用。

若人物位於漢字文化圈：

* 能可靠確認歷史漢字姓名者，優先使用原有漢字姓名。
* 不得把已有漢字姓名的東亞人物重新按外語發音音譯。
* 無法確認漢字原名時，才依實際原語與歷史背景採保守音譯。

現代真人、作曲家、演奏者、製作人員 credit 若為玩家可見文字，也需中文化。

music_player 中所有玩家可見：

* 曲名。
* 版本名。
* 作曲家。
* 演奏者。
* 樂器。
* 曲目介紹。

均翻成繁中。

只有真正受保護 token/key 保留原樣。

## 二十二、不確定項目的自行處理

若遇到不確定的：

* 專名。
* 歷史制度。
* 官職。
* 宗教詞。
* 詞義。
* glossary contextual 適用性。
* 英文工程句型。

不得直接猜測，也不要僅因不確定就停止整個 Batch。

處理順序：

1. 檢查最新版 glossary。
2. 檢查 localization key 與相鄰同組 key。
3. 檢查完整事件組／NAME-DESC／positive-negative 配對。
4. 檢查 placeholder 與 scope 類型。
5. 依「台灣繁中術語與外部資料查證優先順序」先確認原文實際指涉。
6. 再依台灣來源優先序確認既有譯名。
7. 若使用中文維基百科判斷台灣用語，必須確認臺灣正體（zh-tw）顯示結果。
8. 必要時使用原語、第一手、學術、專業或 EU5 機制資料交叉驗證。
9. 仍無法完全確認時，選擇**最保守、語義透明、最少自行添加資訊**的可用譯法。

不得因追求「精確歷史名稱」而假裝已考證成功。

若不同資料產生衝突，優先判斷：

* 是否其實是不同實體。
* 是否為不同時代名稱。
* 是否為外稱、自稱或後世名稱。
* 是否為中國大陸與台灣不同譯名。
* 是否為一般繁中與臺灣正體不同用語。
* 是否為 source 本身可能存在誤拼、錯序或文化錯置。

若 source 疑似存在問題：

* 不得僅因外部資料不同就自行大幅改寫。
* 必須先確認證據是否足夠。
* 若固定 glossary 已有裁定，服從 glossary。
* 若 glossary 未裁定，採最保守且不製造錯誤歷史資訊的譯法。

若原文實際語意已可可靠確認，只是存在多種都正確的中文寫法：

* 不得因某一版本最接近英文句法，就優先選它。
* 應優先選擇台灣繁中母語者在相同文體與歷史語域下更自然的表達。
* 若兩種寫法語意完全相同，優先選擇較清楚、流暢、少翻譯腔且時代語域適切者。
* 若自然化可能改變原意，則回到較保守的語意處理，再重新尋找自然中文句型。

必須理解：

> **語意判斷可以保守，但中文句法不需要保守地貼著英文。**

也必須理解：

> **中文可以現代讀者容易理解，但不等於可以把前現代制度現代化。**

這些判斷仍要納入內部 QA，但除非使用者另外要求，最終回覆**不要輸出 QA、疑點清單或研究過程**。

---

## 二十三、每個 Batch 必做 QA

所有 QA 必須實際執行，但除非使用者另有要求，**不要在最終回覆中顯示 QA 內容**。

這些 QA 屬於**首版譯文輸出前的內部品質控制**。

不得先輸出一個較差版本，再另做第二輪翻譯或第二版 review。

真正寫入輸出檔案的第一版，就應是完成以下檢查後的成熟譯文。

### A. key／集合／順序

* 本批輸出 key 與本批實際 `missing_keys` 完全一致。
* key 數一致。
* key 順序符合 source 原始順序。
* 不得漏 key。
* 不得重複 key。
* 不得把上下文已翻譯 key 當成新增翻譯。
* 本批後重新計算：
  `remaining_missing_keys = source_keys - current_translated_keys`

### B. 行與結構

* 行數合理。
* YAML/localization 結構未破壞。
* 語言標頭與必要縮排正確。
* 不得因 parser 格式差異漏掉 entry。

### C. token multiset

逐 entry 比對：

* `$...$` multiset。
* `[...]` multiset。
* `@...!` multiset。
* `\n` 數量與位置。
* 數字／script token。

真正受保護 token 的內容與數量不得改變。

### D. formatting tag

不比較 tag 內英文與中文是否相同，而是檢查：

* tag 類型。
* 開啟／關閉數量。
* `#!`。
* 巢狀結構。
* 控制語法。
* 必要空格。

並額外抽取 tag 內玩家可見文字，確認沒有因位於 formatting tag 中而漏翻。

### E. glossary

內部建立 glossary 命中表，至少記錄：

* 原文詞條。
* 詞條類型。
* 指定／候選譯名。
* 出現 key。
* 語義適用性。
* 實際指涉是否相同。
* 實體類型是否相容。
* 實際譯法。
* 檢查結果。

分類至少包含：

* 固定譯名已套用。
* 參考譯名。
* 候選譯名。
* 詞義不適用。
* 實體不同／不適用。
* 受保護 token/key，不適用。
* contextual 語義調整。
* 詞族相關但不可直接套用。

glossary 命中掃描不得只檢查與 glossary key 完全一致的字面形式。

必須同時檢查：

* 大小寫變體。
* 單複數。
* 所有格。
* 不規則複數。
* 動詞第三人稱。
* 過去式。
* 過去分詞。
* 現在分詞。
* 形容詞比較級／最高級。
* 常見名詞派生。
* 常見形容詞派生。
* 人物／群體派生。
* 國名／地名與居民名、民族名、文化名、語言名及形容詞之關係。
* 宗教、思想、學派與其信徒／支持者／形容詞之關係。
* 常見前綴派生。
* 連字號、有無空格與合理正字法變體。
* 可可靠確認的歷史拼寫／轉寫變體。

若正文中的詞形屬於 glossary 詞條的規則性變體或明確語義詞族，必須在 glossary QA 中追溯至其相關核心詞條，不得因字面不完全一致就漏掉 glossary 檢查。

若只是屈折變化而詞義未改變，應檢查是否沿用 glossary 的核心固定譯名。

若派生造成：

* 詞性改變。
* 中心名詞改變。
* 實體類型改變。
* 人物／制度／地點／宗教／語言等類型改變。

則必須標示為詞族相關後進一步判斷，不得機械要求與核心詞條使用完全相同的中文字串。

若只是同詞根、字串相似，但實際詞義或實體類型不同，應標示：

`詞族相關但不可直接套用`

不得當成 glossary 漏套。

若完整派生詞、複合詞或片語本身已存在 glossary 詞條，必須優先使用完整詞條，不得讓基礎詞族推導覆蓋完整 glossary 命中。

若語義與實際指涉均適用的固定詞條未套用，必須先修正再完成 Batch。

### F. 台灣繁中與專名 QA

對本批出現的高風險專名，額外檢查：

* 是否存在台灣官方／學術／專業既有譯名。
* 是否誤把簡體中文直接簡轉繁。
* 是否把香港／澳門用語誤當台灣慣例。
* 若引用中文維基百科，是否確認臺灣正體（zh-tw）顯示結果。
* 是否只看搜尋結果摘要而未確認實際來源。
* 是否把同名不同人物／神祇／文化／宗教誤當同一實體。
* 是否把現代名稱錯套到 EU5 時代。
* 是否把外稱、自稱與後世名稱混為一談。
* 音界號是否只是因原文空格而機械加入。
* 宗教、文化、地名、國名是否無必要地加入音界號。
* 是否存在 source 本身疑似錯拼、錯序或文化錯置而未經確認就擅自修正。
* 是否把前現代制度名稱現代化。
* 是否將已有文化內生術語的概念泛化成現代功能詞。

### G. 語意 QA

至少抽查 3～5 個高風險 key，優先：

* 多義詞。
* 歷史制度。
* 冷門專名。
* 因果句。
* 長 desc。
* 複雜 placeholder。
* glossary contextual 判斷。
* glossary 詞族／詞形判斷。
* key 與 value 共同消歧。
* comparator trigger。
* formatting tag 內專名。
* 台灣／簡中譯名有差異的專名。

確認：

* 無摘要。
* 無漏句。
* 無主受詞反轉。
* 無因果改變。
* 無錯誤時態。
* 無條件邏輯改變。
* 無程度改變。
* 無自行增加資訊。
* 無因 glossary 詞形不同而漏套固定核心術語。
* 無因詞族相似而把不同概念錯誤翻成同一詞。
* 無把中國大陸譯名直接簡轉繁當成台灣固定譯名。
* 無因未確認 zh-tw 而把中文維基其他地區版本誤當台灣用語。
* 無為追求中文自然度而改變歷史制度或文化身分。
* 無為追求歷史感而增加 source 不存在的古典修辭。

### H. 特殊 placeholder QA

檢查：

* `GetHerHis`／`GetHisHer` 等所有格代名詞：
  必須暫時將 placeholder 分別替換為「他」與「她」，閱讀完整繁中句子，確認是否依中文句法正確補入或省略「的」。若替換後出現「他頭顱」「她性命」「他忠誠」等不自然領屬結構，必須修正；若為「在他手中」「在她肩上」「在他眼前」等自然中文慣用結構，則可省略「的」。
* 主格／受格代名詞。
* `GetFlavorRank`。
* 語言／方言 placeholder。
* 文化名稱 placeholder。
* 一般概念 token 中心名詞。
* token 與中文邊界空格。

### I. 排版 QA

檢查：

* 不應出現全形斜線 `／`。
* 中文標點全形。
* token 間無不必要半形空格。
* formatting tag 控制語法空格未被破壞。
* 不出現「我國[country|e]」「首都[capital|e]」等中心名詞重複。
* 音界號 `·` 未因原文空格而機械濫用。

### J. 首版中文母語品質 QA

本項不是只抽查 3～5 條。

**本 Batch 中所有長 desc、事件敘述、歷史敘事、短文章與複雜完整句都必須在輸出前完成此檢查。**

此檢查屬於第一次翻譯本身的一部分，不另產生第二版。

暫時只閱讀完成中的繁中譯文，檢查：

* 如果不知道原文是英文，這句是否仍像自然台灣繁中？
* 是否仍能明顯看出英文句法骨架？
* **是否能從中文逐段反推出 `which / that / whom / in order to / with / of / by / in return for / as well as` 等英文結構？若可以，而且中文因此顯得生硬，應重新組句。**
* 是否存在「中文沒錯，但不太像母語者會寫的句子」？
* 是否有不自然的名詞化。
* 是否有不必要的被動結構。
* 是否有英文介系詞結構硬搬。
* 是否有過度冗長的目的句或因果句。
* 是否有不自然的「僅僅是……的存在」「使……得以……」「將……置於……」等結構。
* 是否可以用更直接、成熟的中文表達。
* 是否有代詞銜接問題。
* 是否有上下句稱呼跳動。
* 是否有不必要的同義詞替換。
* 是否有句子長度或資訊順序明顯不適合中文。
* 是否有某幾條品質明顯低於本組其他譯文。
* 是否為追求順口而把歷史制度或前現代語彙改得過度現代。
* 是否為追求「歷史味」而讓原本平實的 source 變得過度文言、華麗或戲劇化。

如果發現問題，**直接修改尚未輸出的首版譯文**。

不得把：

> 「沒有明顯翻錯」

當成此項通過標準。

修改完成後，再與英文 source 對照，確認自然化沒有造成：

* 資訊遺失。
* 資訊新增。
* 主受詞改變。
* 條件改變。
* 因果改變。
* 程度改變。
* 時態改變。
* 機制改變。
* token 破壞。
* 歷史制度或文化身分被改寫。

### K. 事件組整體中文品質

若 Batch 包含同一事件組的：

* title。
* desc。
* option。
* tooltip。
* follow-up event。
* policy explanation。
* 同一事件鏈的多段敘述。

必須把玩家可見文字作為**同一組中文文本**閱讀。

檢查：

* 是否像同一款遊戲、同一組事件中的文字。
* 文體是否一致。
* 人稱是否一致。
* 同一概念是否無故改譯。
* 上下文是否自然銜接。
* 前一句建立的稱呼，後一句是否無故換稱。
* 是否出現某一句非常成熟、另一句明顯直譯的品質落差。
* 是否因批量翻譯而留下大量相同英文式句型。
* 同一事件組的歷史語域是否一致。
* 是否有某一條突然使用現代行政／企業語彙，而其他句子仍維持前現代語感。
* 是否有某一條為追求古典感而過度文言化。

若單條語意都正確，但整組閱讀時存在明顯品質落差，應直接在首版輸出前修正。

## 二十四、完成判定

每完成一個 Batch，都必須重新從目前完整繁中檔或已完成翻譯 key 集合計算真正進度。

不得使用：

`前一批累計 + 本批輸出行數`

直接推算。

必須計算：

`remaining_missing_keys = source_keys - current_translated_keys`

並確認：

`已完成 missing key + 尚未完成 missing key = 最初 missing key universe`

當所有 Batch 編號看似完成時，仍必須做最終：

`source_keys - final_translated_keys`

只有結果為空集合，才能宣告：

`本檔全部 Batch 已完成`

Batch 編號處理到最後一批，不等於 100% 完成。

最終還要確認：

* `final_translated_keys` 涵蓋全部 `source_keys`。
* formatting tag 內沒有無合理原因殘留的漏翻外語。
* 所有 token／placeholder 結構完整。
* 所有本次補翻 missing key 都存在於最終成果中。

## 二十五、批次進度追蹤

請從工作開始時建立完整 Batch 狀態。

每完成一個 Batch，內部更新：

* 本次完成 Batch。
* 累計已完成 Batch。
* 尚未處理 Batch。
* 本次 key 範圍。
* 本次 key 數。
* 累計 missing key 完成數。
* 尚未完成 missing key 數。
* 整體進度百分比。

累計 key 進度必須依實際集合計算。

若 Batch 重新拆分／合併：

* 更新完整 Batch 清單。
* 更新各 Batch key 範圍。
* 更新總批次數。
* 更新完成／未完成狀態。
* 不得沿用已失效的舊 Batch 總數。

## 二十六、最終回覆限制

所有 parser 檢查、glossary 掃描、研究、翻譯、token QA、格式 QA、語意 QA、歷史語境判斷、台灣繁中術語查證以及首版中文母語品質控制仍必須完整執行。

但完成一個實際翻譯 Batch 後，**最終回覆只顯示**：

1. 進度追蹤：

   * 本次 Batch。
   * key 範圍。
   * key 數。
   * 累計完成。
   * 尚未處理。
   * 整體進度。
   * 是否「本檔全部 Batch 已完成」。

2. 本次產生的下載檔案連結。

不要在最終回覆輸出：

* 翻譯內容全文。
* 第二版翻譯。
* QA 報告。
* glossary 命中表。
* 語意說明。
* 中文潤稿分析。
* 研究過程。
* 專名考證過程。
* 外部資料查證過程。
* 其他補充。

所有中文母語化、自然度修正、歷史文化語域校準及語意確認，必須在**第一次寫入輸出檔案之前**完成。

不得採：

> 先輸出較保守／較直譯版本，再另做第二輪 review 或第二版修訂

作為常規流程。

首版輸出本身即應是可直接使用的成熟翻譯。

若本次只是首次建立 Batch 規劃、尚未翻譯任何 Batch，則只回覆 Batch 規劃與進度，不產生虛假的翻譯下載檔。

若使用者當前明確要求的是**單一術語討論、譯名比較、專名考證或翻譯理由**，而不是實際 Batch 翻譯，則不受本節「只顯示進度與下載檔」限制；應直接回答該術語問題並說明必要理由。

## 二十七、最終原則摘要

任何時候都不得以：

* 格式省事。
* Batch 編號。
* 單一 regex。
* 官方簡中字面。
* 簡體直接轉繁體。
* 未確認地區版本的中文維基頁面。
* 英文表面詞義。
* 英文表面句法。
* 英文原句資訊順序。
* glossary 單字字面命中。
* glossary 完全字串一致比對。
* 粗糙 stemming。
* 現代中文直譯。
* 原文空格直接轉成音界號。
* 「看起來差不多」。
* 「中文文法沒錯」。
* 「意思大致看得懂」。
* 「現代台灣人日常比較常這樣說」。

取代對：

* 完整 source key universe。
* 實際遊戲機制。
* 原文真正指涉。
* 完整事件上下文。
* 歷史文化語域。
* 原語與文化內部語境。
* glossary 語義適用性。
* glossary 詞形／詞族關係。
* 台灣既有譯名。
* 臺灣正體（zh-tw）用語。
* token／placeholder 結構。
* 台灣繁中母語自然度。
* 完整句子的中文資訊結構。
* 同事件組的文體一致性。
* 前現代制度與文化身分的時代適切性。

的實際判斷。

glossary 的目的不是要求正文必須與 glossary key 在英文表面形式完全一致，而是確保**同一核心概念及其合理詞形／詞族變體能被辨識並一致處理**。

固定 glossary 的目的也不是用來取代實體辨識。

正確順序必須是：

**先確認原文實際指涉 → 再確認 glossary 是否語義適用 → glossary 未固定時再依台灣繁中來源優先序選擇譯名。**

若固定 glossary 在當前語義中確實適用，則不得因臨時搜尋到另一個譯法就靜默更改；若認為 glossary 本身值得修訂，必須另行交由使用者裁定。

同時不得因詞族關係而抹除：

* 詞性差異。
* 人物／制度差異。
* 國名／居民名差異。
* 宗教／信徒差異。
* 神祇／宗教差異。
* 民族／語言差異。
* 名詞／形容詞差異。
* 單數／複數以外的語義差異。
* 歷史制度中的實體類型差異。

對完整句、desc、事件敘述及短文章，必須額外遵守：

> **先完整讀懂英文想說什麼，再以成熟台灣繁中重新表達完全相同的意思。**

不得採：

> 英文片語 A → 中文片語 A
> 英文片語 B → 中文片語 B
> 英文片語 C → 中文片語 C
> 最後把三段拼接

作為長文本主要翻譯方式。

應採：

> **理解完整命題 → 判斷語氣與資訊焦點 → 判斷歷史文化語域 → 以中文重新組織 → 遮住 source 進行母語編輯 → 回查原文命題**

以上皆在**第一次翻譯輸出之前一次完成**。

首版譯文應同時滿足：

### 語意上

沒有：

* 漏譯。
* 增譯。
* 主受詞改變。
* 因果改變。
* 條件改變。
* 程度改變。
* 時間關係改變。
* 可能性／必然性改變。
* 遊戲機制改變。

### 中文上

拿掉英文 source 後，不應讓台灣繁中母語者明顯感覺：

> 「這是一句照著英文結構翻出來的中文。」

同時也不得讓熟悉相關歷史文化的讀者感覺：

> 「這明明是前現代制度，卻被寫成現代政府、企業或日常用語。」

目標是產出：

**完整、不漏翻、不破壞遊戲語法、glossary 詞形與詞族辨識可靠、實體辨識可靠、歷史與機制語義可靠、優先符合台灣既有譯名與臺灣正體用語，並且讓玩家可見的完整句、desc、事件敘述與短文章在首版就達到成熟、自然、流暢且歷史文化語域適切的台灣繁中母語品質，可直接投入 EU5 localization。**

最終原則：

> **忠實的是意思，不是英文句型。**

> **自然的是中文句法，不是把歷史文本現代化。**

> **歷史感來自正確的制度詞彙、文化語域與原文文體，不是刻意文言化。**

> **自然不是自由改寫，而是用成熟中文表達完全相同的意思。**

> **第一版就必須是完成品，不把中文品質問題留給第二輪修訂。**
